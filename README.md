# flowkit

A shared collection of Claude Code commands and skills built to help engineering teams get more out of AI-assisted development. It isn't tied to any single workflow — today it covers turning underspecified tasks into a scoped implementation plan before code gets touched, reviewing your own work before you open a PR, both sides of pull request review (triaging and reviewing other people's PRs, then working through the feedback left on your own), and keeping comments and diffs clean before merge. New commands and skills get added as the team finds more places AI assistance pays off.

Packaged as a plugin so a team can install and update these as a single unit, instead of copying files into `~/.claude/commands` by hand.

## What's included today

**Commands** (`commands/`)

| Command | Purpose |
|---|---|
| `/pr-review-loop` | Finds every open PR that needs your attention — never reviewed, or with new commits/comments since your last review — and loops through them one at a time: pulls the PR description plus every inline review thread and comment from `gh`, checks out the branch, sizes up the diff, then resolves the ticket's title/description from `tickets/sprint.csv` — asking you for it only when the key isn't in there — and confirms which depth to review at. Runs `/review-quick` by default, or the full multi-agent `/review-pr` when the PR earns it. Pass `full` (`/pr-review-loop full`) to default every PR to the deep pass. |
| `/pr-review-parallel` | The same queue, reviewed concurrently instead of one at a time. Every PR gets its own git worktree, so your working tree is never touched and a dirty repo is no obstacle — and because the worktree is built from `refs/pull/<n>/head`, fork PRs behave like any other. Every `gh` call and every fetch happens in the parent up front, sequentially, so the agents that follow never touch the network — which is what makes running them at once safe. Subagents can't ask you anything, so the questions move: one batched ask for whatever `tickets/sprint.csv` couldn't resolve before the fan-out, then findings walked through a PR at a time after it. Pass `full` for the deep pass, or explicit numbers (`/pr-review-parallel 839 841`) to skip the queue scan. Tells you the agent count before spending it. |
| `/review-quick` | Fast single-pass review of an open PR against ticket context. Pulls CI status from the PR instead of re-running lint/tests locally, and prints findings pre-formatted as copy/paste-ready GitHub PR comments — it never posts anything itself. Reads the PR's existing inline threads first, so anything a colleague (or you, last round) already commented on lands in an "Already raised on this PR" section instead of the paste list. Remembers past passes per PR so a finding you saw and chose not to comment on isn't re-flagged unless it's gotten worse. |
| `/review-pr` | Thorough multi-agent review of an open PR — up to six parallel agents (bugs, regressions, quality, risk, test coverage, and ticket/discussion alignment), scaled down when a diff doesn't warrant all of them. The alignment agent judges the diff against the PR's inline review threads as well as the ticket: unresolved threads the head doesn't answer, resolved ones whose fix isn't visible in the code, and outdated ones whose point still stands. Takes ticket context inline from `/pr-review-loop`, or falls back to `ticket.md` and then to a ticket-key lookup in `tickets/sprint.csv`, and reads lint/test/build results from the PR's CI rather than running them locally. Slower and more expensive than `/review-quick` — use it for anything genuinely high-risk or unusually large, not for triaging a queue. |
| `/review-and-fix` | `/review`, then act on it. Runs the full pre-PR review, triages every finding into fix / ask / skip / verify (High-risk and failing checks always get fixed; Low-risk nits in untouched files don't, because widening the diff costs the next reviewer more than it's worth), confirms the split with you, specs the whole batch through `preflight-spec`, implements, and re-runs the checks. Edits code; never commits, pushes, or opens a PR. |
| `/review` | Pre-PR review of **your own** work, before anyone else sees it. Reviews branch commits *plus* staged, unstaged, and untracked changes against `ticket.md`, falling back to the branch's ticket key in `tickets/sprint.csv`, and asking you only if neither has it. No PR means no CI, so it runs the repo's lint, tests, and build itself, once, then fans out the same multi-agent pass. Also greps for the debris you don't want a reviewer finding: stray `console.log`, focused tests, new `TODO`s, hardcoded keys, localhost URLs. Ends on a Ready / Fix first / Needs a decision verdict. Reports only — it doesn't edit unless you ask. |
| `/address-pr-comments` | The other side of a review: on your own feature branch, pulls every *unresolved* comment thread on the PR, runs `preflight-spec` over the whole batch to research and scope the work, implements it, then verifies thread-by-thread that each point is actually addressed. Prints copy-paste-ready replies, including an explicit "no reply needed" where that's the right call. Built to be re-run as review rounds go by: it remembers what it already addressed, so a follow-up review surfaces only genuinely new comments and reviewer pushback on earlier fixes. Never posts, commits, or pushes. |
| `/comment-cleanup` | Reviews comments in your *uncommitted* diff and deletes/shortens ones that don't earn their keep. Never touches code, never adds new comments. |
| `/review-best-practices` | Structured code-quality review (DRY, separation of concerns, naming, complexity, plus an Angular-specific dimension when the repo looks like Angular) against the current branch vs. its base. |

**Skills** (`skills/`)

| Skill | Purpose |
|---|---|
| `preflight-spec` | Auto-loads for vague/underspecified coding tasks. Turns the ask into a short goal/non-goals/acceptance-criteria/verification spec and gets confirmation before editing production code. Both editing commands (`/review-and-fix`, `/address-pr-comments`) route their whole batch of work through it as a single spec rather than one per item, since fixes tend to overlap. |
| `humanize` | Rewrites user-facing prose so it reads like a person wrote it: no em dashes, no AI stock phrasing, varied sentence rhythm, every fact and number preserved. Invoke it directly on any text, or let the review commands call it, since they now run every PR comment and reply through it before printing. |

**Scripts** (`scripts/`)

- `pr-needs-review.sh` — deterministic backing script for the "which PRs need me" step in `/pr-review-loop` and `/pr-review-parallel`. Run from inside a `gh`-authenticated repo; outputs JSON. Kept as a plain script (not re-derived by the model each run) because the filtering logic here is pure timestamp/state comparison, not judgment.
- `pr-worktree.sh` — owns the git worktree lifecycle behind `/pr-review-parallel`. `add <n>` fetches `refs/pull/<n>/head` and checks it out detached under `<git-common-dir>/flowkit/worktrees/pr-<n>`; `remove <n>`, `remove --all`, `list`, and `prune` clean up after. Four deliberate choices: fetching the *pull* ref rather than a remote branch means fork PRs resolve like any other; living inside the git dir means the worktrees never show up in `git status` and never need a `.gitignore` entry; checking out detached means they never collide with the local branches `gh pr checkout` leaves behind for `/pr-review-loop`; and every ref it writes — the PR head *and* the base branch it diffs against — goes under `refs/flowkit/`, so `add` never reaches into refs the user owns. That last one isn't hypothetical: `HEAD` is a legal branch name, and a forced fetch into `refs/remotes/origin/HEAD` writes straight through that symref onto your `origin/main`. Adding a worktree writes nothing to the working tree of the repo you run it from, which is what lets a review run against a dirty tree. Every subcommand prints one JSON object carrying `ok`; unlike `ticket-lookup.sh`, failure exits non-zero, because a worktree that didn't get created is a real error rather than a miss to route around. Removal and prune are idempotent, so an interrupted run costs the next one nothing. Cleanup is scoped by hand rather than delegated to `git worktree prune`, which is repo-global and would happily deregister a worktree you built for your own work that happens to live on a drive you haven't mounted today.

  Two review runs in one repo don't collide. Each mints an id with `run-id` and passes `--run <id>` to every call; worktrees get locked with that id via `git worktree lock`, and removal and pruning skip anything a live run holds — reporting it in `held[]`/`skipped[]` and exiting 3 for a partial teardown, rather than silently doing less than asked. The claim lives in git's on-disk lock state, which is the point: two Claude Code sessions share no memory, so a note in a command document can't coordinate them and a lock can. Liveness comes from a marker under `<git-common-dir>/flowkit/runs/`, not from how old the lock is — a run parked for an hour waiting on your answer is still live, while a run that died holds nothing. `--force` overrides, and a worktree *you* locked by hand is never touched without it.
- `test-pr-worktree.sh` — `bash scripts/test-pr-worktree.sh`, no arguments, no setup. Builds throwaway repos in a temp dir, stubs `gh`, and checks `pr-worktree.sh` end to end: that `add` leaves a *dirty* tree byte-identical down to the index, that fork PRs and force-pushes resolve, that a failed removal reports failure instead of a cheerful `ok: true`, that cleanup survives symlinked repo paths and paths with spaces or backslashes, that pruning never touches a worktree the user made, and — driving two simulated runs against one repo — that neither can tear down the other's work. It exists because this is the only script in the repo that deletes things.
- `pr-comment-threads.sh` — same idea for `/address-pr-comments`: fetches the unresolved comment threads, review summaries, and PR comments on the current branch's PR, excluding resolved threads and your own comments, and outputs JSON with a stable id per item. Uses GraphQL `pullRequest.reviewThreads` because thread *resolution state* isn't available from `gh pr view --json comments` or the REST comments endpoint — which is precisely why it's a script and not something the model reassembles each run.
- `ticket-lookup.sh` — resolves a ticket key to its title, description, and acceptance criteria from `tickets/sprint.csv`, so `/review`, `/review-quick`, `/review-pr`, `/pr-review-loop`, and `/pr-review-parallel` stop asking you to paste text the repo already holds. Takes `<TICKET-KEY> [--csv <path>]`, always exits 0, always prints one JSON object — a miss is `{"found": false, "reason": ...}`, never an error, so a review is never blocked by a missing or broken CSV. It's a script rather than model-side CSV reading for the usual reason plus a sharper one: a Jira export is hundreds of columns wide with commas and newlines inside quoted cells, and eyeballing the right row out of that is exactly the kind of thing to hand to a parser. Column matching is by normalized header name against an ordered candidate list, so the export's own names and generic ones both resolve.
- `pr-review-threads.sh` — the reviewer-side counterpart, used by `/pr-review-loop`, `/pr-review-parallel`, `/review-pr`, and `/review-quick`. Takes an optional PR number (defaults to the current branch's PR) and returns the description, every inline review thread, the review summaries, and the PR conversation. The filtering is deliberately the inverse of `pr-comment-threads.sh`: that one answers "what do I still have to act on" and so drops resolved threads and your own comments, while this one answers "what has already been said here" and drops nothing — a thread you opened last round and a thread the author already resolved are both things you need before writing the same comment twice. Every thread comes back flagged with `is_resolved`, `is_outdated`, and `authored_by_me`. Worth knowing why this can't be `gh pr view --json body,comments,reviews`: those `reviews[]` nodes carry only the *summary* body a reviewer typed above their line comments, and the line comments themselves are absent at any depth. On `cli/cli#9000` that fetch returns 3 review bodies and none of the 2 inline comments, without erroring.

## Generated comment style

`/review-pr`, `/review-quick`, `/pr-review-parallel`, `/review-best-practices`, and `/address-pr-comments` all produce text that gets pasted into GitHub, so they share two output rules:

- **Code tokens are backticked.** Identifiers, file paths, flags, types, and literal values go in backticks so GitHub renders them as code. A bare `some_name` in prose loses its underscores to markdown emphasis.
- **Every comment body goes through the `humanize` skill before printing.** Phrasing only; paths, line numbers, severities, and code are untouched.

`/review` is deliberately outside this. Nothing it prints is going on a PR — it's your own work, read by you — so it skips the `humanize` pass and the comment formatting entirely and just says what's wrong and what to do about it.

## Requirements

- `gh` CLI, authenticated against the target repo's GitHub remote (`gh auth status`)
- `git`, `jq`
- `python3` — only for `tickets/sprint.csv` lookups. Without it that step reports a miss and the commands ask you for the ticket instead, exactly as they did before
- Run from inside the target git repository — these commands operate on "the current repo/branch," they don't take a repo argument
- `/address-pr-comments` additionally needs an open PR for the branch you're on, since it resolves the PR from the current branch rather than taking a number
- `/review-pr` and `/review-quick` need an open PR too — they read CI results and discussion from it. `/review` is the one command with no `gh` requirement at all: it works on a local branch, or on nothing but uncommitted changes
- `/pr-review-parallel` needs git 2.17+ (for `git worktree remove`) but explicitly *not* a clean working tree — it's the one review command that doesn't care what's uncommitted, since it never checks anything out where you're working

## Notes on state

- Two different things stop a review from repeating itself, and they aren't interchangeable. The **inline threads** on the PR are public and live — a finding matching one gets routed to "Already raised on this PR" rather than into the paste list, in every one of the PR review commands, because a second copy of an existing comment doesn't make the point twice. The **review memory** below is private and per-machine: it only records what *you* decided about a finding. Neither is ever written on the other's behalf, and a resolved thread disappearing from the fetch is the correct way for that state to expire.
- `/review-quick`'s per-PR memory lives at `~/.claude/pr-review-memory/<owner>__<repo>/<pr-number>.json` on each user's own machine — this is personal reviewer state (what you chose to comment on vs. skip), not something the plugin ships or syncs. Nothing to configure. `/review-pr` reads the same file but never writes it and never suppresses on it: a full pass re-surfaces findings a quick pass dismissed, marked as previously seen, because looking again is the whole point of the deeper pass. `/review` has no memory at all — there's no PR to key it to. `/pr-review-parallel` uses the same files with the same rules, with one structural difference: its review agents only ever *read* them, and the parent does every write after you've said which findings you're posting. A subagent can't ask you that question, so it has no business recording the answer.
- Where lint/tests/build come from is the main split between the PR commands and the pre-PR one. `/review-pr`, `/review-quick`, and `/pr-review-parallel` read them off the PR's CI checks and never run them locally. `/review` runs them itself, once, before any agent spawns, because nothing has been pushed and CI has never seen this code.
- `ticket.md` is read by `/review` (it's your own ticket, that's the normal case) and, as a fallback, by `/review-pr`. Neither ever writes it. Inside `/pr-review-loop` and `/pr-review-parallel` it isn't touched at all: the ticket title/description is resolved per PR and passed inline, so reviewing other people's work can't overwrite a `ticket.md` holding your own.
- `tickets/sprint.csv` is the fallback beneath `ticket.md`, and the only ticket source `/pr-review-loop` and `/pr-review-parallel` read. Drop a Jira CSV export there and the commands stop asking you to paste ticket text they can look up: they pull the key out of the PR title or branch name and read the row for it. Column names are matched dynamically — a Jira export's `Issue key` / `Summary` / `Description` / `Custom field (Acceptance Criteria)` works, and so does a hand-written `id,title,description` file. Acceptance criteria, when present, reach the alignment agent as their own field rather than buried in the description. Everything degrades quietly: no file, no key in the file, or a CSV that won't parse just puts you back to being asked. Read-only, always — no command writes to it, including to correct a stale row. The commands name the source and key they resolved, so a stale export is visible rather than silently believed.
- `/address-pr-comments` keeps its own per-PR memory at `~/.claude/pr-comment-memory/<owner>__<repo>/<pr-number>.json` — deliberately a separate namespace, because it's author-side state (feedback you received and what you did about it) rather than reviewer-side state. Entries are keyed by GitHub's stable thread node id, so they survive threads being resolved and renumbered between review rounds.
- Worktrees are `/pr-review-parallel`'s only on-disk footprint, and they live at `<git-common-dir>/flowkit/worktrees/pr-<n>` — inside the git directory, so they never appear in `git status` and never need a `.gitignore` entry. Alongside them sits one small marker file per run under `<git-common-dir>/flowkit/runs/`, which is how concurrent runs tell each other apart. The command tears its own worktrees down when it finishes, prunes leftovers before it starts, and cleans up even on a run that ends badly. `scripts/pr-worktree.sh prune` handles anything that still slips through, and `prune --force` reclaims what a run that died is still nominally holding.
- None of these commands push, commit, or post to GitHub on your behalf. `/pr-review-loop`, `/pr-review-parallel`, `/review-quick`, and `/review-pr` are explicitly display-only by design — you copy the comments they generate into GitHub yourself. `/review` reports and stops too; it offers to apply its own fixes at the end and waits for you to say yes. `/review-and-fix` and `/address-pr-comments` are the two commands that edit code: one acting on its own review, the other on your reviewers' comments. Both stop at the working tree — reviewing, committing, pushing, and replying stay with you.

## Install

```bash
claude plugin marketplace add https://github.com/eriks-briedis/claude-flowkit
claude plugin install flowkit@eriks-briedis
```

## Update

After a new version is pushed:

```bash
claude plugin marketplace update eriks-briedis
claude plugin update flowkit@eriks-briedis
```

(Claude Code also re-syncs marketplaces periodically in the background; the above forces it immediately.) A restart of your Claude Code session is required for the update to take effect.
